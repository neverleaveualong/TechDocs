# TechDocs PR 작성 규칙

## 필수 Git 작업 흐름

`main`은 직접 수정하거나 직접 푸시하지 않고 PR을 통해서만 변경한다.

1. 작업 시작 전 로컬 `main`과 원격 `main`의 최신 상태를 확인한다.
2. 작업 내용에 맞는 별도 브랜치를 생성한다.
3. 해당 브랜치에서 코드 또는 문서를 수정하고 검증한다.
4. 검증된 변경만 작업 브랜치에 커밋한다.
5. 작업 브랜치를 원격 저장소에 푸시한다.
6. 원격 작업 브랜치에서 `main`을 대상으로 PR을 생성한다.
7. CI와 변경 내용을 확인한 후 승인된 PR만 병합한다.

- 브랜치 이름은 `feature/작업명`, `fix/작업명`, `refactor/작업명`, `docs/작업명`, `chore/작업명` 형식을 사용한다.
- 커밋 메시지는 `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`처럼 변경 성격이 드러나는 접두사를 사용한다.
- 하나의 브랜치와 PR에는 하나의 명확한 목적만 포함한다.
- 사용자가 명시적으로 병합을 요청하지 않은 경우 AI 에이전트는 PR 생성 후 링크만 보고하고 병합하지 않는다.
- `main` 직접 반영은 긴급 상황에서 사용자가 명시적으로 승인한 경우에만 허용한다.

## 기본 원칙

- PR은 `요약 → 문제점 → 원인 → 한 것 → 결과` 순서로 작성한다.
- 각 항목은 한 문장에 한 가지 내용만 담은 `-` 불릿으로 작성한다.
- 불필요한 수식어, 반복 설명 및 과장된 표현을 사용하지 않는다.
- 파일 목록만 나열하지 말고 변경 이유와 사용자 또는 시스템에 미치는 영향을 설명한다.
- 수치가 있다면 변경 전후를 함께 적고, 확인하지 않은 결과는 예상이라고 표시한다.
- 해당 사항이 없으면 `- 해당 없음`으로 작성한다.

## 항목별 작성 기준

### 요약

- PR의 목적과 핵심 변경을 1~3개 불릿으로 설명한다.

### 문제점

- 변경 전 발생했던 오류, 불편 또는 기술적 한계를 설명한다.

### 원인

- 문제를 만든 코드, 구조, 데이터 또는 설정상의 원인을 설명한다.
- 원인을 확인하지 못했다면 추측을 사실처럼 쓰지 않는다.

### 한 것

- 실제 구현하거나 수정한 내용을 설명한다.
- 중요한 설계 선택과 영향 범위를 포함한다.

### 결과

- 테스트, 빌드, 측정 또는 직접 확인한 결과를 설명한다.
- 아직 검증하지 못했다면 검증하지 못한 이유와 남은 확인 사항을 적는다.
