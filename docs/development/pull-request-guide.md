# TechDocs PR 작성 규칙

## 기본 원칙

- PR은 `요약 → 문제점 → 원인 → 한 것 → 결과` 순서로 작성한다.
- 각 항목은 한 문장에 한 가지 내용만 담은 `-` 불릿으로 작성한다.
- 불필요한 수식어, 반복 설명 및 과장된 표현을 사용하지 않는다.
- 파일 목록만 나열하지 말고 변경 이유와 사용자 또는 시스템에 미치는 영향을 설명한다.
- 수치가 있다면 변경 전후를 함께 적고, 확인하지 않은 결과는 예상이라고 표시한다.
- 해당 사항이 없으면 `- 해당 없음`으로 작성한다.

## 항목별 작성 기준

### 요약

- PR의 목적과 핵심 변경을 1~3개 불릿으로 설명한다.

### 문제점

- 변경 전 발생했던 오류, 불편 또는 기술적 한계를 설명한다.

### 원인

- 문제를 만든 코드, 구조, 데이터 또는 설정상의 원인을 설명한다.
- 원인을 확인하지 못했다면 추측을 사실처럼 쓰지 않는다.

### 한 것

- 실제 구현하거나 수정한 내용을 설명한다.
- 중요한 설계 선택과 영향 범위를 포함한다.

### 결과

- 테스트, 빌드, 측정 또는 직접 확인한 결과를 설명한다.
- 아직 검증하지 못했다면 검증하지 못한 이유와 남은 확인 사항을 적는다.
