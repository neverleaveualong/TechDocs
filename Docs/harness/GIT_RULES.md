# Git, 커밋 및 PR 규칙

## 브랜치 작업 흐름

1. 작업 시작 전 원격 `main`의 최신 상태를 확인한다.
2. 로컬 `main`을 원격 `main`과 동기화한다.
3. 작업 내용에 맞는 별도 브랜치를 생성한다.
4. 해당 브랜치에서 코드 또는 문서를 수정하고 검증한다.
5. 검증된 변경만 커밋하고 원격 작업 브랜치에 푸시한다.
6. 원격 작업 브랜치에서 `main`을 대상으로 PR을 생성한다.
7. CI가 통과하고 변경 내용을 확인한 PR만 병합한다.
8. 병합 후 로컬 `main`을 원격 `main`과 다시 동기화한다.

- `main`에는 직접 커밋하거나 직접 푸시하지 않는다.
- 브랜치 이름은 `feature/작업명`, `fix/작업명`, `refactor/작업명`, `docs/작업명`, `chore/작업명` 형식을 사용한다.
- 하나의 브랜치와 PR에는 하나의 명확한 목적만 포함한다.
- 사용자 요청 없이 PR을 자동 병합하지 않는다.

## 커밋 규칙

커밋 메시지는 다음 접두사를 사용한다.

| 접두사 | 사용 범위 |
| --- | --- |
| `feat:` | 새로운 기능 |
| `fix:` | 오류 수정 |
| `refactor:` | 동작을 유지하는 구조 개선 |
| `docs:` | Markdown 및 설명 문서 변경 |
| `test:` | 테스트 추가 또는 수정 |
| `chore:` | 설정, 의존성 및 기타 유지보수 |

- 제목은 변경 결과가 드러나는 명령형 문장으로 간결하게 작성한다.
- 서로 다른 목적의 변경을 하나의 커밋에 섞지 않는다.
- 테스트하지 않은 내용을 커밋 메시지에서 검증된 것처럼 표현하지 않는다.

## PR 본문 규칙

PR은 다음 순서를 유지하고 각 항목을 짧은 `-` 불릿으로 작성한다.

1. 요약
2. 문제점
3. 원인
4. 한 것
5. 결과

- 파일 목록만 나열하지 말고 변경 이유와 영향 범위를 설명한다.
- 추측이나 과장 대신 실제 변경과 검증 결과를 작성한다.
- 해당 사항이 없으면 `- 해당 없음`으로 표시한다.
- 검증하지 못한 항목은 이유와 남은 위험을 작성한다.
- `.github/pull_request_template.md`를 사용한다.
- `.pr-body.md`, `.pr-body-*.md` 등 임시 PR 본문 파일을 생성하거나 커밋하지 않는다.

## 병합 규칙

- PR의 대상 브랜치가 `main`인지 확인한다.
- 필수 CI가 통과했는지 확인한다.
- 병합 충돌과 예상하지 못한 변경 파일이 없는지 확인한다.
- 사용자가 병합을 요청한 경우에만 병합한다.
- 병합 후 원격 작업 브랜치를 삭제하고 로컬 `main`을 최신 상태로 동기화한다.
