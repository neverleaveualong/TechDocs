# TechDocs 리팩토링 Pain Points

이 문서는 2026년 8월 10일 기준 전체 코드, 설정, 테스트 및 배포 구성을 점검해 정리한 리팩토링 백로그입니다. 항목은 현재 동작과 외부 계약을 먼저 검증한 뒤 작은 단위로 수정하며, 해결한 내용은 관련 테스트와 설계 문서에 반영한 후 이 문서에서 제거하거나 완료 상태로 갱신합니다.

## 우선순위 기준

| 우선순위 | 의미 |
| --- | --- |
| P0 | 결과의 정확성, 사용자 흐름 또는 보안·비용에 직접 영향을 주므로 가장 먼저 해결 |
| P1 | 데이터 정합성, 운영 안정성 및 확장성을 위해 P0 다음으로 해결 |
| P2 | 유지보수성과 개발 품질을 높이기 위해 구조 개선 과정에서 해결 |

## P0: 사용자 결과와 외부 계약

### 1. ClaimLens Backend·Frontend 이벤트 계약 불일치

- Backend는 도구 결과를 `tool`, `data`로 전달하지만 Frontend 일부 코드는 `tool_name`, `result`를 읽습니다.
- 차트 데이터도 Backend의 camelCase 필드와 Frontend의 snake_case 필드가 섞여 있고, 후보 특허의 중첩 구조도 서로 다릅니다.
- 이 상태에서는 분석은 완료돼도 기능 목록, 후보 특허 및 비교 차트가 화면에 표시되지 않을 수 있습니다.
- `Docs/API.md`를 단일 계약으로 삼아 이벤트 타입을 정의하고, Backend serializer와 Frontend parser가 같은 fixture를 사용하는 계약 테스트를 추가합니다.

완료 조건: 대표 ClaimLens SSE fixture로 기능 추출, 후보 선택, 청구항 비교 및 차트 렌더링이 모두 검증됩니다.

### 2. 검색 결과가 없을 때 생성 답변의 근거 부족

- 검색 결과가 없어도 기존 검색 프롬프트는 특허를 찾았다는 형식의 답변을 요구할 수 있습니다.
- 출처가 없는 특허명, 출원번호 또는 비교 내용이 생성될 위험이 있습니다.
- 검색 결과가 없는 상태를 별도 분기로 처리하고, 근거가 없으면 결과 없음과 다음 검색 방법만 안내합니다.

완료 조건: 검색 결과 0건 테스트에서 임의의 특허 정보가 생성되지 않고, 출처가 있는 내용만 응답에 포함됩니다.

### 3. 검색 답변 생성의 LLM 중복 호출

- Agent graph에서 답변을 생성한 뒤 스트림 Service가 같은 요청으로 다시 답변을 생성하는 흐름이 있습니다.
- 응답 지연과 비용이 증가하고, 내부 결과와 사용자에게 보이는 결과가 달라질 수 있습니다.
- 답변 생성 책임을 한 계층으로 모으고, 나머지 계층은 해당 결과를 스트리밍하거나 전달만 하도록 정리합니다.

완료 조건: 사용자 검색 한 번에 최종 답변 생성이 한 번만 실행되며 스트림·비스트림 결과의 의미가 일치합니다.

### 4. 비용 발생 API의 보호 장치 부족

- 수집, KIPRIS 조회, ClaimLens 및 LLM 호출 경로에 인증, 호출 제한 또는 충분한 입력 상한이 없습니다.
- 긴 질의, 큰 페이지 수 및 과도한 `top_k`는 비용 증가와 서비스 고갈로 이어질 수 있습니다.
- 인증·권한 정책을 정하고 요청 길이, 페이지 수, 결과 수, 동시 실행 수 및 시간 제한을 API 경계에서 검증합니다.

완료 조건: 비인가 호출, 상한 초과 요청 및 반복 호출이 명시적인 상태 코드로 차단되고 관련 테스트가 존재합니다.

## P1: 데이터와 실행 안정성

### 5. 관계형 DB 스키마 마이그레이션 부재

- 현재 `create_all()` 중심 초기화는 새 테이블 생성에는 유용하지만 기존 컬럼, 제약 조건 및 인덱스 변경과 rollback을 관리할 수 없습니다.
- 운영 DB가 PostgreSQL인 만큼 본격적인 스키마 리팩토링 전에 Alembic 체계를 두는 편이 안전합니다.

권장 도입 순서는 다음과 같습니다.

1. SQLAlchemy 모델과 실제 운영 DB 스키마 차이를 먼저 확인합니다.
2. 현재 스키마와 동일한 baseline migration을 만듭니다.
3. 기존 DB에는 검증 후 `alembic stamp`, 신규 DB에는 `alembic upgrade head`를 적용합니다.
4. 중복 행과 고아 데이터를 점검한 뒤 unique, check, cascade 및 index를 각각 작은 migration으로 추가합니다.
5. downgrade 가능 여부와 백업·복구 절차를 배포 전에 검증합니다.

Pinecone 재색인과 SQLite FTS 재구성은 관계형 스키마 migration과 수명 주기가 다르므로 Alembic에 섞지 않고 별도의 버전 있는 작업으로 관리합니다.

완료 조건: 빈 DB와 기존 DB 모두 같은 최신 스키마에 도달하고 upgrade·downgrade 검증 절차가 문서화됩니다.

### 6. 특허 재수집 시 벡터 중복과 저장소 간 정합성

- Pinecone 적재에 특허·청크 기반의 안정적인 ID가 없으면 같은 특허를 재수집할 때 벡터가 중복될 수 있습니다.
- 관계형 DB 저장 성공 후 벡터 저장이 실패하는 등 부분 실패가 발생해도 두 저장소를 보상하는 흐름이 분명하지 않습니다.
- 안정적인 vector ID, 특허 단위 교체 정책, idempotency 및 부분 실패 복구 작업을 정의합니다.

완료 조건: 같은 특허를 여러 번 적재해도 행과 벡터 수가 증가하지 않으며 중간 실패 후 재실행으로 일관된 상태를 복구합니다.

### 7. Hybrid 검색의 문서 식별과 확장성

- FTS에 저장한 토큰화 문자열과 벡터 검색의 원문이 서로 다른데 병합 키가 내용 hash를 포함하면 같은 청크가 하나로 합쳐지지 않을 수 있습니다.
- PostgreSQL BM25 계산이 Pinecone 청크 일부만 메모리에 올리는 방식이면 데이터가 늘어날수록 결과가 불완전해질 수 있습니다.
- 저장소 전체에서 공통 `chunk_id`를 사용하고 후보 집합 생성과 RRF 계산 범위를 명확히 합니다.

완료 조건: keyword와 vector가 같은 청크 ID로 병합되며 데이터 규모가 커져도 재현 가능한 평가 결과를 냅니다.

### 8. 스트림 실패 시 전체 검색 자동 재실행

- Frontend가 스트림 오류 후 비스트림 검색을 자동 호출하면 이미 수행된 수집과 LLM 요청이 중복될 수 있습니다.
- fallback 요청이 취소 신호와 실행 ID를 완전히 공유하지 않으면 취소한 검색의 결과가 뒤늦게 반영될 수 있습니다.
- 재실행 여부를 오류 유형별로 구분하고 모든 요청에 동일한 `AbortSignal`과 실행 식별자를 적용합니다.

완료 조건: 네트워크 중단·사용자 취소·서버 오류별 동작이 테스트되고 한 검색에서 비용 작업이 의도치 않게 반복되지 않습니다.

### 9. 전역 Agent 상태와 checkpoint 수명

- singleton Supervisor의 iteration 같은 mutable state가 요청 사이에 남으면 사용자 요청이 서로 영향을 줄 수 있습니다.
- 고유 thread ID를 계속 쌓는 in-memory checkpoint는 장기 실행 시 메모리가 증가할 수 있습니다.
- 요청별 상태를 graph state로 이동하고 checkpoint 보존 기간과 정리 정책을 정의합니다.

완료 조건: 동시 요청과 연속 요청 테스트에서 상태가 섞이지 않고 종료된 checkpoint가 정책에 따라 정리됩니다.

### 10. async 경로 내부의 동기 I/O

- async API와 스트림 안에서 동기 LLM, Pinecone 및 DB 호출이 실행되면 event loop가 막힐 수 있습니다.
- 비동기 client를 사용하거나 제한된 worker thread로 옮기고 timeout과 취소 전파를 함께 적용합니다.

완료 조건: 느린 외부 호출 중에도 다른 health·API 요청이 처리되며 timeout과 취소가 정상 동작합니다.

### 11. 시작·상태 확인과 오류 노출

- DB 초기화 실패를 숨긴 채 health가 항상 정상으로 응답하면 배포 시스템이 장애를 감지하지 못합니다.
- 자동 수집 오류의 내부 exception 이름과 메시지가 스트림을 통해 사용자에게 노출될 수 있습니다.
- readiness는 필수 의존성 상태를 반영하고, 사용자 응답은 안전한 공통 메시지로 제한하며 상세 원인은 서버 로그에 남깁니다.

완료 조건: 의존성 장애 시 readiness가 실패하고 응답·로그의 민감정보 노출 검사가 통과합니다.

### 12. 파괴적인 운영 스크립트

- demo seed 스크립트는 주요 테이블을 삭제하고, 특허 seed 스크립트는 Pinecone index 전체 삭제를 실행할 수 있습니다.
- 실행 환경 allowlist, 명시적 확인, 대상 namespace 표시, dry-run 및 백업 절차를 추가합니다.

완료 조건: 운영 환경 또는 대상 미지정 상태에서 삭제가 실행되지 않으며 dry-run으로 변경 범위를 확인할 수 있습니다.

## P1: 배포와 품질 게이트

### 13. CI 검증 범위 부족

- 현재 CI는 제한적인 Python compile·import와 Frontend build 위주여서 Backend 테스트와 Frontend lint 실패를 막지 못합니다.
- Backend `unittest`, Frontend lint, TypeScript 검사 및 build를 필수 job으로 구성하고 필요하면 계약 테스트를 별도로 둡니다.

현재 점검 기준은 다음과 같습니다.

- Backend compile: 통과
- Backend `python -m unittest discover -s tests -v`: 31개 통과
- Frontend `npx tsc --noEmit`: 통과
- Frontend `npm run build`: 통과
- Frontend `npm run lint`: 11개 오류, 2개 경고로 실패
- Frontend 자동화 테스트: 없음

완료 조건: 로컬 하네스와 CI가 같은 명령을 사용하고 필수 검증 실패 시 PR 병합이 차단됩니다.

### 14. Docker 실행 계약 불일치

- Backend healthcheck가 `curl`을 사용하지만 slim image에 설치되지 않았다면 정상 컨테이너도 unhealthy가 될 수 있습니다.
- `NEXT_PUBLIC_API_URL`은 브라우저 bundle의 build-time 값인데 runtime에만 주입하면 반영되지 않을 수 있고, 브라우저에서 `backend:8000` 주소를 해석할 수도 없습니다.
- image에 실제 존재하는 healthcheck 도구를 사용하고 Frontend public API URL을 build·배포 환경 기준으로 분리합니다.

완료 조건: clean build한 compose 환경에서 Backend healthcheck와 브라우저 API 호출이 모두 성공합니다.

### 15. 의존성과 평가 환경의 재현성

- 일부 Python 의존성은 버전이 고정되지 않았고 사용하지 않는 패키지가 설치돼 재현성과 image 크기에 영향을 줄 수 있습니다.
- 평가 코드가 운영 namespace와 다른 Pinecone 범위를 사용하면 개선 전후 수치가 실제 서비스 품질을 나타내지 못합니다.
- 직접 의존성 버전을 고정하고 미사용 패키지를 제거하며 평가 dataset·namespace·golden truth의 근거와 버전을 기록합니다.

완료 조건: 동일 lock 또는 requirements로 환경을 재현할 수 있고 운영 검색 설정과 같은 조건에서 회귀 평가를 실행합니다.

## P2: Frontend와 유지보수성

### 16. Frontend 타입·표시 규칙 분산

- ClaimLens 결과 처리에 `any`가 남아 계약 불일치를 compile 단계에서 찾지 못하고 있습니다.
- 상태·점수·품질 등급 변환이 컴포넌트마다 달라 실제 결과와 다른 문구가 표시될 수 있습니다.
- API event union과 domain type을 만들고 표시 변환을 한 곳에서 관리합니다.

완료 조건: `any` 없이 스트림 이벤트가 좁혀지고 Backend 상태별 UI 문구와 점수 계산이 테스트됩니다.

### 17. LLM Markdown 의존 UI와 접근성

- AI 답변을 고정된 Markdown 모양으로 직접 분해하면 모델 출력 형식이 조금만 달라져도 내용이 사라질 수 있습니다.
- 결과 modal에는 focus trap, 최초 focus 및 닫힌 뒤 focus 복귀 같은 접근성 동작이 필요합니다.
- 가능한 결과는 구조화된 schema로 전달하고 Markdown은 표현 계층에서 렌더링하며 modal keyboard 동작을 검증합니다.

완료 조건: 형식이 다른 정상 응답도 내용이 보이고 keyboard만으로 modal을 열고 탐색하고 닫을 수 있습니다.

### 18. 주석과 파일 책임 설명의 신뢰도

- 전체 코드에는 오래된 헤더, 번호·이모지 중심 주석 및 실제 동작을 반복하거나 과장하는 표현이 섞여 있습니다.
- 모든 파일에 주석을 한 번에 추가하면 검증되지 않은 설명만 늘어날 수 있습니다.
- 동작을 먼저 검증한 뒤 실제로 수정하는 파일 단위로 책임 헤더와 변경 이유를 갱신하고 불필요한 주석을 제거합니다.

완료 조건: 수정된 파일의 상단 책임과 주요 주석이 현재 코드와 일치하며 코드만 반복하는 주석이 남지 않습니다.

## 권장 리팩토링 순서

1. ClaimLens 이벤트 계약과 화면 표시를 맞춥니다.
2. 검색 결과 0건 처리와 LLM 중복 생성을 해결합니다.
3. 비용 API의 인증, rate limit 및 입력 상한을 추가합니다.
4. Alembic baseline과 DB 변경 절차를 마련합니다.
5. 안정적인 vector·chunk ID와 저장소 정합성을 확보합니다.
6. 전역 상태, async blocking 및 스트림 재실행 문제를 해결합니다.
7. Backend 테스트, Frontend lint·typecheck·build를 CI 필수 검증으로 만듭니다.
8. Docker와 평가 환경을 운영 조건에 맞춥니다.
9. 수정하는 파일부터 타입, 컴포넌트 책임 및 주석을 정리합니다.

각 단계는 동작 수정과 대규모 파일 이동을 한 PR에 섞지 않고, `Docs/API.md`와 `Docs/DATABASE.md`의 계약 변경 여부를 함께 확인합니다.
